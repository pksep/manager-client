# manager: контракт виджета 0.1

Обновлён 15.09.2026. Реализован в клиенте, `manager-server` и `demo/server.ts`;
демосервер предназначен для проверки интерфейса. Общие типы:
[`src/protocol.ts`](../src/protocol.ts).

## Подключение

Загрузчик создаёт скрытый iframe. Сообщения между страницей и iframe
проверяются по origin, окну отправителя и случайному идентификатору экземпляра.
CSS сайта не проникает внутрь. Нажатия за пределами круглой кнопки/меню
не перехватываются пустой областью iframe.

`mount({siteId, serviceUrl, widgetUrl, offset?})` возвращает `destroy()`.
Сервис и страница виджета используют HTTPS; HTTP разрешён только localhost.
Публичный siteId не является служебным ключом или подтверждением личности.

Перемещение открытого окна использует внутреннее сообщение
`{type:'sep-manager:move', instance, phase, x, y}` с теми же проверками отправителя.
`start/move/end` передают экранные координаты указателя; `nudge` — смещение
стрелками клавиатуры. Загрузчик ограничивает позицию размерами экрана и хранит
её в памяти до destroy/перезагрузки. Это взаимодействие страницы и iframe;
сервис сообщений не участвует.

Файл, выбранный в виджете, поступает в тот же процесс отправки без
промежуточного предпросмотра. Для первого обращения сначала запрашиваются
контакты; для текущего сразу выполняются загрузка и отправка. Контракт HTTP,
проверка лимитов и идентификаторы для повторной доставки остаются прежними.

## HTTP и канал событий

База: `${serviceUrl}/v1/widget`. Гостевой токен передаётся в заголовке
`Authorization: Bearer ...`; cookies не используются. Токен и черновик
живут в памяти страницы, не записываются в localStorage.

Отдельный подписанный `visitorToken` хранится в localStorage только для общего
лимита браузера. Он не заменяет гостевой токен и не открывает историю.

| Метод и маршрут | Вход | Результат |
| --- | --- | --- |
| POST `/session` | `{siteId, source, visitorToken?}` | `{token, visitorToken?, config, serverTime, inquiryId, messages}` |
| WebSocket `/events` | Первое сообщение `{type:'authenticate', token}` | `ready` с текущим снимком переписки |
| POST `/inquiries` | `SendRequest`, включая contacts | `{inquiryId, message}` |
| POST `/inquiries/:id/messages` | `SendRequest` текущего обращения | `{inquiryId, message}` |
| POST `/attachments` | FormData: `file`, `operationId`; заголовок `X-Operation-Id` с тем же значением | `{id, name, size, mime}` |
| GET `/attachments/:id` | Гостевой токен | Байты доступного этому гостю файла |

`SendRequest`: `{operationId, html, attachmentIds, contacts?}`.

Сервер может вернуть `403 {code:'captcha_required', siteKey, challenge}`. Виджет
получает токен Яндекс SmartCaptcha и один раз повторяет ту же операцию с
`X-Captcha-Token` и `X-Captcha-Challenge`, сохраняя тело и operationId. Ключи
сервера не передаются. Отмена/ошибка проверки оставляет форму для повтора.
Ответ 429 содержит `Retry-After`; ошибка проверки файла — 422, недоступность
антивируса — 503. CORS разрешает перечисленные заголовки и показывает Retry-After.
`contacts`: `{name, phone, email}`. Идентификаторы сообщений, обращения,
операций и вложений являются непрозрачными строками.

`Message`: `{id, inquiryId, direction, author, html, attachments, createdAt,
operationId?, avatarUrl?, readAt?}`. Направление `outgoing` означает сообщение посетителя, `incoming`
— ответ менеджера. createdAt — ISO 8601; operationId связывает ответ сервера
с попыткой отправки посетителя.

`avatarUrl` — необязательный публичный HTTPS-адрес аватара автора (локальный
HTTP разрешён только для разработки). Учётные данные и исполняемые URL
отклоняются. Без изображения штатный Avatar показывает инициалы.
`readAt` — необязательная дата ISO 8601, которую выставляет сервис после
прочтения сообщения менеджером. Без неё виджет показывает одну галочку
«Отправлено», с ней — две «Прочитано». Прочтение одного из менеджеров достаточно;
назначенный ответственный на этот статус не влияет. Сам посетитель не может
установить этот признак через SendRequest.

Обновление статуса передаётся событием `{type:'message', message}` с тем же id.
Клиент обновляет существующую запись, не создаёт дубль и не сбрасывает
прочтение при запоздавшем подтверждении отправки. Снимки `/session` и `ready`
также содержат readAt, чтобы статус переживал восстановление соединения.
Контакты показаны из памяти текущей страницы после подтверждения первой
отправки и используют время/прочтение того же обращения; дополнительная
запись сообщения не создаётся.

События:

```json
{"type":"ready","inquiryId":null,"messages":[]}
```

После подписки сервер передаёт актуальный снимок, затем упорядоченные
`{type:'message', message}`. Снимок должен быть согласован с началом подписки:
сообщения между ответом `/session` и установкой WebSocket не должны теряться.
Наличие старого снимка в `/session` само по себе не разрешает показ виджета.

Клиент отправляет `{type:'ping'}` каждые 10 секунд; сервер отвечает
`{type:'pong', serverTime}`. Нет ответа за 5 секунд — весь виджет скрывается.
Явное закрытие WebSocket скрывает его сразу. Начальная сессия и handshake
имеют отдельные таймауты по 5 секунд. Повторы: 1, 2, 4, 8, 16, 30 секунд.
При возврате вкладки на экран связь проверяется заново; после восстановления
показывается свёрнутая кнопка, не открытое окно.

## Конфигурация

```json
{
  "company": {"name":"НПО Амотив"},
  "welcomeMessages": ["Здравствуйте!", "Поможем с подбором.", "Напишите нам."],
  "socialLinks": [{"label":"Написать ВКонтакте","url":"https://vk.com/","icon":"vk"}],
  "schedule": {"timezone":"Europe/Moscow","start":"08:00","end":"18:00","days":[1,2,3,4,5]},
  "contactPolicy":"all",
  "limits":{"fileBytes":10485760,"fileCount":5,"messageChars":10000}
}
```

company.avatarUrl необязателен. Дни — 0 (воскресенье) … 6 (суббота).
Проверяются границы времени и смена через полночь. Часы клиента корректируются
по serverTime. `contactPolicy`: `all` либо `name-and-one`; во втором режиме
введённый неверный дополнительный контакт также блокирует отправку.
Иконки ссылок: `vk`, `telegram`, `chat`. Сами ссылки не принимают сообщения
из соцсетей. Неизвестные/опасные протоколы URL не допускаются.

## Доставка и границы истории

Первая попытка отправки открывает контактную форму. До её подтверждения
сообщение и выбранные файлы остаются на странице. Форма не теряет данные
после ошибки, повторная отправка заблокирована во время запроса.

Повтор одного действия использует прежний operationId; для каждого файла
используется `${operationId}:${index}`. Сервис должен обеспечивать атомарную
дедупликацию, возвращать прежний результат и проверять неизменность полезной
нагрузки. Если подтверждение HTTP потеряно, operationId в снимке позволяет
клиенту увидеть доставленное сообщение и очистить черновик без повторного лида.

Виджет принимает только сообщения текущего inquiryId. Новая загрузка страницы
создаёт новую гостевую сессию и не запрашивает прошлую историю. Совпадение
телефона/email и объединение карточки клиента не расширяют гостевые права.

HTML ответов очищается; исполняемые элементы, обработчики событий, стили и
встроенные внешние изображения не вставляются в переписку. Файлы скачиваются
отдельным запросом с токеном, без публичных путей внутреннего хранилища.

## Обязанности производственного сервиса

Сервер должен проверять настройки сайта, гостевую сессию и принадлежность
каждого обращения/вложения, ограничения размера/количества/содержимого и частоты
запросов. source — сведения о странице, не доверенный признак полномочий.
`ready` подтверждает готовность приёма для этой сессии, включая рабочий путь
сохранения сообщений/файлов. Успешный healthcheck процесса этого не заменяет.

Хранение, повторы после перезапуска, очистка временных загрузок, истечение/
обновление гостевых сессий, интеграция канонических методов чата и ЕРП
реализуются на этапе 2. Демо хранит всё в памяти, имитирует менеджера и
доступно только на loopback; его `__demo`-маршруты не входят в этот контракт.
